# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

MQ Sports ERP: a Flutter app (package `a2_stocks`, folder `a2_stocks`) for Android, iOS, Windows, macOS, Linux and the web, talking to the backend API in the sibling repository `c:\src\a2_stocks_api` (NestJS + PostgreSQL; see its `README.md`, `docs/target_stack.md`, `docs/api_design.md`). The **source code is the source of truth**; the markdown specs in this repo's root are partly outdated (see "Doc drift").

- **Mobile and desktop** are offline-first: a local SQLite database (Drift) plus a queue of unsent actions, synced with the API.
- **Web** is online-only: no local database, every action is an API call (`docs/web_admin.md`).
- There is **no Firebase and no Hive any more**. `firestore.rules`, `firebase.json` and the Android `google-services` setup are leftovers that can be deleted.

## Commands

- `flutter pub get` · `flutter run` · `flutter analyze` (lints: `flutter_lints`, strict casts/inference)
- `dart run build_runner build` after changing `lib/data/local/tables.dart` (regenerates `app_database.g.dart`, which is committed).
- `flutter test` runs the unit tests. Two real-server suites are skipped unless asked for (`--dart-define=RUN_API_TESTS=true --dart-define=API_BASE_URL=...`, API on an EMPTY database with one admin login): `test/online/api_flow_test.dart` (web mode) and `test/data/offline_flow_test.dart` (a day without internet with two devices). Commands are at the top of each file.
- Web: `flutter run -d chrome --web-port 8080 --dart-define=API_BASE_URL=http://localhost:3000` (see `docs/web_admin.md`). Desktop: `flutter run -d windows`.
- Imports are always absolute: `package:a2_stocks/...`.

## Development rules

- Production-ready code only: no `// TODO`, no stubs. Explicit types everywhere (`final List<X> x = ...`), avoid `dynamic`, immutable models with `final` fields, null-safe.
- **No hard-coded text.** Every word a person reads lives in [lib/l10n/app_en.arb](lib/l10n/app_en.arb), never in the code (`test/core/no_hardcoded_text_test.dart` fails on `Text('...')`, `labelText: '...'`, `title: '...'` in screens and widgets). Widgets: `context.l10n.someKey` (`import 'package:a2_stocks/l10n/l10n.dart'`); code without a `BuildContext` (providers, error messages, receipts, enum labels): `L10n.current.someKey`, which `MqSportsApp` keeps on the language being shown. Text with values is an ICU message with typed placeholders (`{count, plural, =1{...} other{...}}`, never "item(s)" or `n == 1 ? '' : 's'`). **A new language is one more file**: copy `app_en.arb` to `app_<code>.arb`, translate the values, run `flutter gen-l10n` (`flutter run`/`test` do it too); untranslated keys fall back to English (`lib/l10n/untranslated.json`, rewritten by `gen-l10n`, lists what each language still lacks: check it before releasing a language); `dateLong`/`dateShort` hold the date patterns. Left-to-right languages only so far (right-to-left needs a layout check; the receipt PDF font is Latin only). **API errors** carry a `code` and `params` (`c:\src\a2_stocks_api\docs\error_codes.md`): `exceptionFor` ([lib/online/api_client.dart](lib/online/api_client.dart)) writes a known code in the app's language through the generated [lib/online/api_error_text.dart](lib/online/api_error_text.dart) (keys `apiError<Code>` in the .arb) and keeps the server's English `message` for an unknown code; `AppException.code` is for logic, never compare error text. When the API adds a code, regenerate (dump `ERRORS` to JSON, then run the generator; it rewrites `api_error_text.dart` and the `apiError*` keys). Not translated on purpose: the product name, text the server writes into records (`ServerText`, ledger/stock descriptions, activity-log text from `GET /v1/logs`), product/category/customer names, and the starter packs (curated on the server, in English). Enum names get their words in [lib/l10n/model_labels.dart](lib/l10n/model_labels.dart) (the models stay pure Dart): `status.label`, `role.label`, `type.labelFor(party)`; module titles and groups are `ErpModule.title(l10n)` / `ModuleGroup`.
- Expected failures are `AppException` subclasses (`lib/core/errors/app_exceptions.dart`): `RemoteSyncException` (server unreachable or failing), `AuthFailureException`, `PermissionDeniedException`, `ValidationException` (also what 400/404/409 from the API become). Catch `AppException`, expose via `AsyncValue.error` / `reportFailure`; never crash the UI.
- Models are pure Dart: dates as ISO-8601 strings; ids are client-side `Uuid().v4()`; each has `toMap/fromMap/copyWith` and implements `SyncableModel`. The JSON keys of `toMap` are the API's JSON keys.
- Permissions are enforced twice: in notifiers (`canManage…Provider` → `PermissionDeniedException`) and by the API. **The server has the final say.** Roles: `admin`, `manager`, `staff` (`UserRole`; unknown → staff).
- Money/stock derive from append-only records rather than stored totals (see below).

## Architecture

Layers: `models` → `data` / `online` (storage and API) → `providers` (Riverpod 2.x) → `screens`/`widgets`. Screens only talk to providers.

`app.dart`: `_AuthGate` (login) → `_AccessGate` (needs an active user, else `AccessDeniedScreen`; starts the sync controller on mobile/desktop) → `HomeScreen`.

### The repository interface
`Repository<T>` ([lib/repositories/repository.dart](lib/repositories/repository.dart)) is all the providers use: `getLocal`, `getLocalById`, `save`, `delete`, `deleteBlockReason`; plus `PurchaseOperations`, `OrderOperations`, `StockAuditOperations` for the multi-record actions (`confirm`, `cancel`). `DataMode` ([lib/providers/data_mode.dart](lib/providers/data_mode.dart)) picks the implementation: `onlineOnly` on web (`lib/online/online_repositories.dart`), `localFirst` elsewhere (`lib/data/local_repositories.dart`). Each repository provider in `*_providers.dart` makes that choice.

`BaseListNotifier<T>` reads `repository.getLocal()`, does optimistic add/update/delete with rollback, and reloads when `syncTickProvider` increments (bump it after any multi-repo action or sync).

### Mobile and desktop: local database + outbox + sync (lib/data)
- **Live updates** ([lib/online/change_feed.dart](lib/online/change_feed.dart), `ApiClient.openChangeStream`): while signed in, every platform keeps a Server-Sent Events connection to `GET /v1/sync/stream`; a `ready`/`changed` signal (no data) makes the device sync at once (`SyncController.syncNow` on mobile/desktop, `RemoteStore.refresh` on web), a burst counts once, a lost connection is retried with growing pauses (1 s to 30 s; `reconnectNow` when the network returns). The timers (60 s / 30 s) stay as the safety net, so the feed only adds speed. The web uses `fetch_client` for the stream (`stream_client.dart`: the browser's default client does not deliver a response while it arrives).
- **Notifications (the bell)**: `NotificationBell` in the header ([lib/widgets/notification_bell.dart](lib/widgets/notification_bell.dart)) shows the unread count and a list; `notificationsProvider` ([lib/providers/notification_providers.dart](lib/providers/notification_providers.dart)) loads `GET /v1/notifications` at sign-in, on the stream's `notification` signal (and on `ready`) and every 5 minutes, announces new ones as a pop-up (`HomeScreen`) and marks all read when the list closes. The server sends a type and values (`order.web_placed`, `stock.low`, `stock.out`); `notificationText` ([lib/l10n/notification_text.dart](lib/l10n/notification_text.dart)) writes the sentence in the app's language, and an unknown type still shows a plain line. Tapping one opens the order or the low-stock list. It needs a connection (like the activity logs). **Sound and system notifications** ([lib/core/notify](lib/core/notify)): when new notifications arrive, `NotificationAlerts.announce` plays a sound (a synthesised chime for an order, a calmer tone for stock; `assets/sounds`, `audioplayers`) and, when the window is not in front (`appFocusedProvider`, the app lifecycle), shows a system notification (`SystemNotifier`: `local_notifier` on Windows/macOS/Linux, the browser's Notification API on the web via `package:web`, picked by conditional import; phones show none yet; on Windows the first use creates a Start-menu shortcut because the system only shows notifications for a named app). The person's choices (sound on/off, desktop notifications on/off) are kept on the device (`alertPrefsProvider`, SharedPreferences `notify_sound`/`notify_system`) and set under Settings > Notifications, which also has a "Send a test"; the browser asks for permission when the switch is turned on (it only allows that from a tap).
- **Database**: Drift/SQLite with typed relational tables mirroring the server's ([lib/data/local/tables.dart](lib/data/local/tables.dart), mapped to models in `collections.dart`). One database file per signed-in user (`databaseProvider`), so one person's unsent work is never uploaded under another name. It holds only **server-confirmed** data plus the `outbox` and `sync_kv` (cursor) tables.
- **Writes never touch the records.** `LocalRepository.save` queues an outbox entry (`OutboxStore`: coalesces edits of an unsent record, drops a delete of a never-uploaded one; states `pending` / `sent` / `failed`). Actions (`orderConfirm`, `orderStatus`, `orderCancel`, `orderPayment`, `purchaseConfirm`, `purchasePayment`, `ledgerEntry`, `auditConfirm`) are queued as one command each.
- **Reads = confirmed data + queue.** `pending_effects.dart` works out, from the queued commands alone, the order, the stock leaving and the ledger charge the user will cause, so they see their work at once. They are never stored: after upload the server's own records arrive and replace them, and every overlay function skips an action whose records are already there (nothing is shown twice).
- **Sync engine** ([lib/data/sync_engine.dart](lib/data/sync_engine.dart)): upload the queue oldest first, each entry with its own id as `Idempotency-Key` (a lost response cannot double an action); a 4xx marks the entry `failed` with the server's reason (user retries/discards on the Sync screen); a network or 5xx error stops the upload and keeps order. Then download everything since the cursor (`GET /v1/sync/changes`), writing data and the new cursor in ONE transaction. Accepted entries stay (state `sent`) until their records have arrived.
- **Offline sales** are always recorded: orders are uploaded with `recordedOffline: true`, so the server skips its stock and credit-limit refusals (the goods already left). Stock can go negative; the Stock screen flags it.
- `SyncController` ([lib/providers/sync_controller.dart](lib/providers/sync_controller.dart)) syncs by itself: at sign-in, when the connection returns, ~3 s after something is queued, every minute. `syncSummaryProvider` feeds the app-bar chip; `screens/sync_screen.dart` shows the queue.
- **Server calls** are all in one class, `ApiCommands` ([lib/online/api_commands.dart](lib/online/api_commands.dart)), used by both the web repositories and the sync engine. Times go out in UTC, amounts rounded to 2 decimals.

### The business (multi-business server)
The server keeps many businesses in one database and tells the app which one the user works for: sign-in, refresh and `GET /v1/auth/me` carry a `tenant` object (id, shop name, phone, walk-in customer id). `ApiClient` keeps it with the saved session (`currentBusiness`, `rememberBusiness`), so it is known offline; `businessProvider` (`providers/business_provider.dart`, `BusinessInfo` in `models`) exposes it, defaulting to MQ Sports for a session saved before businesses existed. Receipts and WhatsApp use the business's name and phone (`shopInfoProvider`), and the walk-in customer comes from it: never hard-code a walk-in id (`BusinessInfo.isWalkIn`; the dashboard functions and `ReceiptData` take `walkInCustomerId`). The Online store section of Settings shows only for the business that runs the public store (`BusinessInfo.hasOnlineStore`). Every admin/manager has Shop details: the **currency** (`PUT /v1/business`, admin only; existing amounts are not converted) and, for a business without the online store, the shop name and phone for receipts (saved through the same `/v1/store-settings` record). **Currency**: `BusinessInfo.currency` (ISO code, from the server) sets `MoneyFormat` (`core/utils/currency.dart`) whenever `businessProvider` is read, and `formatMoney`, `ReceiptData.money`, the WhatsApp text and every POS amount write it; never hard-code "Rs" (use `MoneyFormat.prefix` / `withSymbol`). `MqSportsApp` re-keys the home tree when the currency changes so every screen repaints. After saving shop details/currency call `businessUpdaterProvider` (it updates the session and the providers without signing in again). The online store (Next.js) and its e-mails are MQ Sports' own, not part of A2 Stocks: they stay MQ-branded and in rupees on purpose.

### Auth
`ApiAuthService` signs in through the API (`ApiClient`: single-flight token refresh, errors mapped to `AppException`s). The refresh token and the user are kept (`SharedPrefsTokenStore`) so the app **opens offline** as the saved user and renews the token when a request first gets through. `currentUserProvider` = server's `/auth/me`, else the saved user. Creating a login (`ApiAuthAdminService`) needs a connection. Users are never deleted: "delete" turns the login off.

### Web (lib/online)
`RemoteStore` is an in-memory copy filled from the sync endpoint (first call = everything, then only changes; polled every 30 s and after each own action). Server timestamps are converted to local time on the way in (`normalizeDates`). See `docs/web_admin.md`.

### Derived data via append-only ledgers
- Stock on hand = sum of `StockLedgerModel.quantity` per variant (`stockOnHandProvider`); `VariantModel` has no stock count. Entries are never edited.
- Party balance = opening balance + `LedgerModel` charges − payments (vendors and customers share `LedgerModel` with `partyType`). Purchase/order paid amount = sum of its ledger payments; payment status is derived (`purchaseStatusFor`).
- Purchases, orders, stock movements and audits are never deletable. Parties and products with history can only be deactivated (local `deleteGuard`s give a quick answer; the server enforces it with foreign keys).

### Referential integrity
The server's PostgreSQL foreign keys and transactions enforce it, so the old sync gaps (a child uploaded under a parent deleted elsewhere) are closed: the server refuses such an action and the entry shows as `failed` for the user to resolve. Keep display names on child records (as `PurchaseItem` does) so history stays readable.

### Activity logs
The server writes every log (in the same transaction as the action, user taken from the login). The app's `ActivityLogger` is a no-op hook; the Activity Logs screen (admin) reads `GET /v1/logs` and needs a connection.

### Adding a module
1. Backend first (`c:\src\a2_stocks_api`): table, endpoints, tests, and the sync collection.
2. Here: model, a Drift table in `tables.dart` + a `LocalCollection` in `collections.dart` (+ `LocalCollections`), `build_runner`; an overlay in `pending_effects.dart` if actions create records; an `ApiCommands` method; an `Online…Repository` and a local repository; the repository provider choosing between them; an `OutboxKind` and its case in `SyncEngine._send`/`_arrived` if it is an action.
3. Add an `ErpModule` (id, title, icon, `allowedRoles`, builder) in [lib/providers/module_registry_provider.dart](lib/providers/module_registry_provider.dart).

## UI and theme
- One light theme, `AppTheme.light()` / `AppColors` in `lib/core/theme/app_theme.dart`. The product is **A2 Stocks** and the colours come from its logo: teal `primary` (the lettering), steel `sky`, dark-blue `navy`, bright `blue`, emerald `teal` (the logo's green, for success/growth/"new"). Red is a separate `danger` (+ `dangerSoft`) and means only that something is wrong (cancelled, unpaid, over limit, out of stock, delete, errors): never use `primary` for that. Logo: `assets/images/a2stocks_logo.png` (full, with the name; sign-in) and `a2stocks_mark.png` (the "A" only; small places) via `BrandLogo` / `BrandLockup` (mark + name). Both PNGs have transparent backgrounds. Receipts print the business's own shop name and, when it has one, its logo (`ReceiptData.logoUrl`; the PDF downloads it, re-encodes the server's WebP as PNG, and leaves it off if it cannot).
- **Per-business branding**: the server's `tenant` object carries `logoUrl` and `brandColor` (`#RRGGBB` or empty = the A2 Stocks teal). Admins set them under Settings > Shop details (logo through the photo upload with `PhotoKind.business`, colour from `brandChoices`, saved with `PUT /v1/business`). `AppColors.primary` / `primaryDark` / `primarySoft` are **runtime getters, not constants** (`AppColors.useBrand`, set whenever `businessProvider` is read; a colour too light for white text is darkened): never write `const` around them, and never use them for "wrong" (that is `danger`). The product's own teal is `AppColors.a2Primary`. `MqSportsApp` re-keys the home tree when currency or colour changes. The header and sidebar show the business logo and name (`BusinessLogo` / `BusinessLockup`; the A2 mark while it has no logo); the sign-in screen stays A2 Stocks. `PoweredByFooter` ("Powered by A2 Stocks · Crafted with love by A2 Devs") sits under every shell page and the sign-in screen, and Help & guide has an About card: keep it, it is the product's credit. `assets/images/mq_logo.png` is MQ Sports' old logo, kept for when MQ uploads its own; it is not bundled.
- `HomeScreen` is the shell: side bar at >= 1000 px wide, drawer below; the page beside it is the dashboard or a module (`ErpModule.group` sets the heading it sits under). The POS opens full screen over the shell. Module screens keep their own `AppBar`, restyled as a page header.
- Dashboard: `screens/dashboard/dashboard_page.dart` (admin/manager; staff get shortcuts), figures in `dashboard_providers.dart` and `dashboard_insights.dart` (pure functions, tested). Charts use `fl_chart`.
- POS (`pos_screen.dart`): top bar with clock, category rail, product grid with +/- steppers, order panel, payment-method tiles (the choice pre-selects the method in the payment dialog), bottom action bar. Below 900 px it is two tabs.
- Font: Inter, bundled in `assets/fonts` (SIL OFL, licence file alongside), set as the theme's `fontFamily`.
- Side bar collapses to icons (button in its header; choice kept in SharedPreferences `nav_collapsed`). Vendors and customers are card grids (`PartyCard` in `party_list_view.dart`, `asCards: true`; pickers keep the compact list). Sales & Orders is a grid of receipt-style `OrderReceiptCard`s. Categories are two data tables (`category_stats.dart` holds the counts).
- Stat cards on list pages: `widgets/stat_strip.dart` (`StatStrip` of `StatItem`s, two per row on a phone) sits above the list on Sales & Orders, Purchases, Products, Stock, Users, Customers and Vendors (the party strip is in `PartyListView` when `asCards`). The figures are pure functions in `core/utils/page_stats.dart` (tested): they cover all records, not the current search/filter. Cancelled orders never count as sales.
- **Starter category packs**: Categories > "Starter packs" (admin/manager; also "Start from a template" when there are no categories) opens `screens/catalog/starter_pack_dialog.dart`: pick a business type, tick groups, add. The packs are curated on the server (`GET /v1/starter-packs`, `POST /v1/starter-packs/:id/apply`, needs a connection); `StarterPackPlan` (`core/utils`) counts new vs already-there categories on the device the way the server does (same name under the same parent, any case, active or not). New categories arrive by the normal sync (`starterPackServiceProvider` pulls after applying).
- Settings is grouped into sections (Profile, Online store for admin/manager, Help & guide): a list on the left at >= 800 px, chips on top below that; the store form has headed groups (Status, Contact & alerts, Checkout & delivery, Stock display). Activity Logs rows carry tags (type, module, record, "n linked"), a short `#id` (first 8 characters of the log id, also searchable), day headings, and a "linked entries" filter by `groupId`.

- Receipt: `widgets/receipt_view.dart` (on screen, also with a Code 128 bar code of the order number) and `core/utils/receipt_pdf.dart` (80 mm PDF, same layout). `showReceiptDialog` shows it with Print/Share/WhatsApp.

## Completed modules (all in `lib/screens/<module>`)
- **Users** (admin) · **Categories** (tree, `category_tree.dart`) · **Products** with nested **Variants** (SKU generator, attributes, cost/sale/wholesale prices, price warnings, `variant_picker`)
- **Customers / Vendors** with balance ledgers, party detail screen, ledger entry dialog, `party_picker`
- **Purchases** (create/confirm, detail, payments, status chip) → feeds **Stock** (read-only stock ledger screen; flags negative stock)
- **Stock Audit** (admin/manager): counted quantities, confirming adjusts stock; history screen included.
- **Low-stock alerts**: `VariantModel.alertThreshold` and `isLowStock()` in `core/utils/stock_alerts.dart`.
- **Executive dashboard** (`dashboard_providers.dart`, admin/manager): computed in the app from the lists (`computeDashboardStats`, unit-tested); the server's `GET /v1/dashboard` gives the same figures (checked by the flow tests).
- **Sales & Orders**: customer required, Retail/Wholesale tag, per-line and per-order discounts, status pipeline Pending → Processing → Shipped → Delivered (+ Cancelled, admin/manager only, not after Delivered), payments, credit limit. A cancelled order is final (the server refuses any later change). **Online-store orders** (`channel` `web`, placed by shoppers on the Next.js store in `c:\src\a2_stocks_api\apps\store`, cash on delivery) arrive through sync like any order: `OrderModel.shippingFee` is part of `totalAmount`, `shippingAddress` holds the delivery details, and the web customers are ordinary customer records. Stock is taken out at checkout; an admin/manager cancels fake orders. The shop's own offline orders never carry a delivery fee. Drift schema is version 2 (the `orders` table gained `shippingFee`, `shippingAddress`, `channel`).
- **POS** (`lib/screens/pos/`, all roles): the counter screen. Product grid with photos, category chips, search that also takes a barcode or SKU + Enter (barcodes are optional), per-line and whole-sale discounts, walk-in customer by default (each business has its own: `businessProvider.walkInCustomerId`, named by the server at sign-in; MQ Sports' is `mqSportsWalkInCustomerId`, created by a server migration so staff and offline devices have it; a walk-in must pay in full) or a named customer (may pay part/none, credit limit applies). Payment dialog: split payments by Cash / Easypaisa / JazzCash / Bank transfer (non-cash needs a transaction no.), cash over the total gives change. The sale is an ordinary order with `channel: 'pos'`; each payment is a customer ledger entry with `paymentMethod`/`paymentRef` (the confirm API takes `payments` instead of `paidNow`; the offline outbox payload carries `payments` and the overlay shows one payment per method). Receipts (`core/utils/receipt.dart`, no tax): 80 mm PDF (`receipt_pdf.dart`, print/save/share through the `printing` package) and a WhatsApp text via a wa.me link; also on every order's detail screen. The PDF font is Latin only (no Urdu yet). Not built: returns/refunds, cash-drawer closing, tax, card terminals. Drift schema is version 4 (ledger payment method columns).
- **Photos everywhere** (`lib/online/photo_service.dart`, `lib/widgets/photo_widgets.dart`): products have up to 10 photos (add, delete, make main; `ProductModel.images`, stored as JSON in the Drift `products.imagesJson`); users, categories, customers and vendors have one photo each (`photoUrl`). The file is chosen with `file_picker`, checked on the device (JPEG/PNG/WebP by content, 10 MB), uploaded straight to storage with a link the API signs (`/v1/photos/:kind/:id/...`, `/v1/products/:id/images/...`), then the changed record is pulled back (web: RemoteStore refresh, others: sync pull). Photos need a connection and a record the server already has; saving a form never sends photo fields (the explicit `ApiCommands` bodies leave them out), forms pass `photoUrl`/`images` through `copyWith` so the local copy stays right. Drift schema is version 3.
- **Settings** (all roles; `lib/screens/settings/settings_screen.dart`): your profile photo, the welcome guide, and for admin/manager the online store settings (`/v1/store-settings`, only admin saves; "Send test e-mail" checks the server's SMTP).
- **Welcome guide** (`lib/screens/onboarding/`): role-specific pages (staff, manager, admin with a first-setup checklist) shown once per person per device after sign-in (`OnboardingGate` in the home screen, flag in SharedPreferences, `OnboardingStore.version` shows a changed guide again); reopened from Settings.
- **Sync screen** + `sync_status_chip` (queue, refused entries with Retry/Discard, Sync now, download everything again). On web an "Online" chip replaces it.
- Module access: categories/products/customers/stock/sales = admin+manager+staff; vendors/purchases = admin+manager; users and Activity Logs = admin. Staff may create orders, advance status and record payments; the server sends staff no vendors, purchases or audits.
